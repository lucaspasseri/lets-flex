## Status definitions

- `Pending`: approved as part of the sequence but not yet active.
- `Active`: the only action that may be implemented.
- `Blocked`: cannot proceed without a decision or prerequisite.
- `Changes requested`: implementation exists but requires corrections.
- `Ready for review`: implementation and verification are finished, awaiting user approval.
- `Completed`: explicitly approved by the user.

Only one action may be `Active`.

The coding agent may move an action from `Active` to `Ready for review`.

Only the user may authorize moving an action from `Ready for review` to `Completed`.

## Active action

### 1. Implement the password-reset token lifecycle

Status: Active

#### Outcome

The application has a provider-independent domain and persistence boundary for
creating, finding and consuming password-reset tokens.

This action must not send email or implement browser forms.

#### Work

- Inspect the authentication schema, repositories and password-hashing boundary.
- Inspect how migrations, seeds and database tests are currently organized.
- Resolve the proposed token lifetime.
- Design the smallest persistence model supporting:
  - token hash;
  - local authentication identity;
  - expiration;
  - consumption;
  - creation timestamp.
- Generate raw tokens with a cryptographically secure random source.
- Hash tokens before persistence.
- Invalidate or supersede previous outstanding tokens for the same local identity.
- Consume the token and replace the password atomically.
- Add focused tests for the lifecycle.

#### Constraints

- Tokens belong to local authentication identities.
- Do not identify a token only by email.
- Do not store or log raw tokens.
- Do not modify Google identities.
- Do not implement Resend integration in this action.
- Do not implement pages or HTTP routes in this action.
- Do not change account-linking behavior.
- Do not add unrelated authentication refactoring.

#### Done when

- a token can be issued for a local identity;
- only its hash is persisted;
- a valid token can be resolved;
- expired tokens are rejected;
- consumed tokens are rejected;
- older tokens are invalidated or superseded;
- password replacement and token consumption are atomic;
- focused tests pass;
- relevant repository verification passes;
- the final diff contains no email or UI implementation.
